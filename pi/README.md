# Сборка и запуск на Raspberry Pi

Все скрипты запускаются из корня репозитория, например `pi/deploy_test_to_pi.sh`.
Адрес Pi по умолчанию — `knight@192.168.68.128`. Другой адрес: первым аргументом (`pi/deploy_test_to_pi.sh knight@192.168.68.XXX`) или переменной `PI`.

## Как устроен запуск на Pi

- Приложение запускает при загрузке systemd-сервис `my-app` (`Restart=always`: если процесс убить, через 2 секунды сервис поднимет его снова).
- Какой бинарник он запускает, задаёт скрипт из `ExecStart`: по умолчанию `~/work/Auto_Cleaner_318D4/start_app.sh`. Его можно переопределить файлом в `/etc/systemd/system/my-app.service.d/`. Посмотреть текущую настройку: `systemctl cat my-app`.
- Настройки (`settingsAutoCleaner.ini`) приложение берёт из папки, где лежит бинарник. У тестового запуска и у автозапуска они могут отличаться.
- Лог автозапуска: `ssh knight@192.168.68.128 journalctl -u my-app -f`.

## Скрипты

| Скрипт | Для чего |
|---|---|
| `deploy_test_to_pi.sh` | **Проверить сборку один раз.** Собирает, кладёт бинарник в `~/work/Auto_Cleaner_318D4/Auto_Cleaner_APPM_rspb` (старый → `.prev`), на время теста останавливает `my-app` и запускает сборку в терминале, лог идёт туда же. После Ctrl+C или обрыва ssh автозапуск включается обратно. Если программа упала, дамп памяти копируется в `../build-rpi/core`. Сборку по умолчанию не меняет. |
| `deploy_default_to_pi.sh` | **Сделать сборку сборкой по умолчанию.** Собирает, находит бинарник, который сейчас запускает `my-app`, показывает его и спрашивает подтверждение. Затем заменяет его (старый → `.prev`) и перезапускает сервис. Путь можно задать явно: `DEFAULT_BIN=/путь pi/deploy_default_to_pi.sh`. |
| `rollback_default_on_pi.sh` | **Вернуть предыдущую сборку по умолчанию.** Меняет местами бинарник автозапуска и его `.prev`, спросив подтверждение, и перезапускает сервис. Повторный запуск возвращает обратно. |
| `sync_sysroot.sh` | **Подготовка к сборке.** Копирует с Pi заголовки и библиотеки в `../rpi-sysroot` (рядом с репозиторием). Нужно один раз и после каждого `apt upgrade` на Pi. |
| `build_cross.sh` | **Только сборка**, без Pi. Собирает в `../build-rpi/Auto_Cleaner_APPM_rspb` и проверяет, что бинарнику хватит glibc/libstdc++ с Pi. Deploy-скрипты вызывают его сами. |
| `pi_common.sh` | Общая часть скриптов (адрес Pi, имя сервиса, окружение eglfs). Сам не запускается. |
| `linux-armhf-g++/` | Настройки qmake для кросс-сборки. Используется `build_cross.sh`. |

## Старые скрипты (`old/`)

Копируют исходники на Pi и собирают прямо на ней (долго). Адреса в них зашиты: `.155`, `.124`, `192.168.0.77`.
Бинарник запускают вручную, поэтому, пока работает `my-app`, сервис его подменяет — см. выше.

| Скрипт | Для чего |
|---|---|
| `old/deploy_to_pi.sh`, `old/deploy_to_pi_124.sh` | Копируют исходники без артефактов сборки, собирают на Pi и запускают (`.155` / `.124`). |
| `old/script_to_build.sh`, `old/script_to_build_local.sh`, `old/script_to_build_local_124.sh` | Копируют исходники, пересобирают на Pi с нуля (`make clean`) и запускают (`192.168.0.77` / `.155` / `.124`). |

## Обычный порядок работы

1. Первый раз: `pi/sync_sysroot.sh`.
2. Проверка правок на машине: `pi/deploy_test_to_pi.sh`, потом Ctrl+C.
3. Если всё хорошо: `pi/deploy_default_to_pi.sh`.
4. Если что-то не так после этого: `pi/rollback_default_on_pi.sh`.
